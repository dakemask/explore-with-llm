# Explore with LLM

Pure-frontend branching chat app. Users bring their own provider + API key; all data lives in the browser (IndexedDB). Deployed as a static site to GitHub Pages (`.github/workflows/deploy.yml`). No backend, no proxy.

The owner is not a programmer and delegates all technical decisions. Requirements are disclosed incrementally — see "Product decisions" below and keep it updated when new ones are made.

## Commands

- `pnpm dev` — dev server
- `pnpm test` — unit tests (vitest)
- `pnpm build` — typecheck + production build into `dist/`
- `pnpm mock` — fake streaming server on :8787 speaking all three protocols, picked by path (see `scripts/mock/server.mjs`; `EXTRA_MODELS=20` lists filler models, for the ≥ 12 picker)

## Verifying UI changes

The owner can't review code, so check changes in a real browser before reporting done:
run `pnpm dev` + `pnpm mock`, then drive the page with `playwright-core` using the locally installed
Chrome (`C:/Program Files/Google/Chrome/Application/chrome.exe`) — install playwright-core in the
session scratchpad, not in this project. Add a provider of any protocol with base URL `http://localhost:8787`;
model `mock-chat` streams plain reasoning + markdown/code/math, `mock-think` streams summary + encrypted reasoning (OpenRouter `reasoning_details` / Anthropic `redacted_thinking` / Responses two summary parts + `encrypted_content`), `mock-tags` puts `<think>` in the content, `mock-bad` returns 401, `mock-cut` drops the connection mid-reply, `mock-empty` streams nothing, `mock-hang` never answers, `mock-name` replies with a short title naming the prompt it got (conversation / side question + context message count), `mock-long` = mock-chat with 40 paragraphs of reasoning (a line every 120 ms, ~5 s) and the reply three times (scroll / sticky tests); Anthropic requests without `max_tokens` get a 400. Every reply starts with a line echoing the request counter, protocol, context size, reasoning echoed back in the context, body fields beyond the protocol's own (i.e. the model's parameters), the number of images in the whole context, and the last user message; image parts of the wrong shape get a 400.

Regression suites live in `scripts/browser/*-suite.mjs`; `run-all.mjs` there runs them in parallel (how: its header).

How much to check depends on whether a change touches a shared concern, not on how big it looks (owner, 2026-10-08: full checks for tiny tasks were too slow; the foundations now make small additions predictable):
- **Small** — text, i18n, tip contents, icons; styles or logic inside one component that touches no shared concern: `pnpm test` + `pnpm build`; if it looks different, one cropped screenshot of that spot, one theme.
- **Medium** — a new small component / menu item built on the existing owners (`Layer`, `Dialog`, `focus.ts`, `useAutoScroll`…) without changing them: the above + the suite of the concern it uses (e.g. a menu → `layers-suite`).
- **Large** — changes a shared concern's owner (`useAutoScroll`, `Layer`, `focus.ts`, `ChatView`'s switch reset, `column.ts`, `useConversationData`), the data model / export format, streaming, or a feature spanning several parts: the full check (all suites, the browser in motion, both themes when styles change).
- Before handing a step to the owner to try, run the full `run-all.mjs` once, so small changes that add up are still checked together.
- Screenshots only for new looks, cropped to the changed area; skip them where a suite already asserts the numbers (positions, widths, jumps). Both themes only when colors / tokens change.

Shortcuts for scripts: seed the provider by writing straight into the `providers` store of the
`explore-with-llm` IndexedDB and reloading (faster than clicking through Settings; raw IndexedDB writes
aren't seen by Dexie live queries until a reload). To wait for a
reply to finish, wait for the Stop button (`aria-label="停止"`) to disappear — the Send button exists
(disabled) even while streaming. To attach an image, make the PNG in the page (`canvas.toDataURL`) and
`setInputFiles` it on `input[accept="image/*"]`; hand-written PNG bytes are easily invalid and silently rejected.
Playwright's `click()` / `hover()` scroll their target into view first, which spoils scroll-position checks:
place things with `scrollTop`, then click with `page.mouse` at the element's box. A programmatic scroll within
1.2 s of a fold / switch / retry is undone by the scroll hold (`useAutoScroll`); wait before scrolling in scripts.
To select text by mouse drag, press on a line (e.g. the box's top + 12 px), not the vertical middle of a
multi-line paragraph — that can land between lines and select nothing (no pill appears).

## Gotchas

- Git Bash heredocs on this machine can eat backslashes. Write files containing `\` (LaTeX, regex) with the Write tool, not heredocs. Long multi-edit Python heredocs also tend to fail to parse; use Write/Edit. Heredocs also mangle non-ASCII (Chinese) text; for scripted multi-edits, write the `.py` to the scratchpad with the Write tool and run it with `PYTHONUTF8=1`.
- Python's `open(..., 'w')` on Windows writes CRLF; the repo is LF (`.gitattributes`). Pass `newline='\n'`.
- Tailwind v4 `translate-*` utilities use the CSS `translate` property, which stacks with `transform` in keyframes. Animations on centered elements must not use `translate()` in `transform`.
- Radix Dialog autofocuses the first button, which opens its tooltip. `Dialog` focuses the panel instead (`onOpenAutoFocus`); keep that for new dialogs.
- Inputs bound to Dexie data must keep local state (IndexedDB writes are async; binding directly drops keystrokes). See `ProviderForm`.
- Anything animating past the viewport edge (e.g. the panel's slide-in) makes Windows Chrome flash a scrollbar and jump the page; the app root has `overflow-hidden` for this — keep it. Headless tests use overlay scrollbars, so check `document.documentElement.scrollWidth` instead of eyeballing.
- Streaming mock replies can finish before a test clicks Stop; run `DELAY=60 pnpm mock` for stop tests.
- Headless Chrome hides scrollbars (overlay-like): pass `open({ scrollbars: true })` (lib.mjs) to see Windows' classic ones, which take width. A position read in `requestAnimationFrame` can be from before our ResizeObserver fix in that frame (not what's painted): to check painted frames, also read in a ResizeObserver created after the app's (see `layout-suite` W3).
- The project has no formatter config; don't run `npx prettier` (its defaults reformat whole files). Match the surrounding style by hand.

## Architecture

- `src/db/` — Dexie schema and data types. **Data model is the core; change it deliberately.**
- `src/lib/colors.ts` — branch colors (`branchColors`: node id → ring index 0–6 or `GREY`, over non-archived main nodes; `parentColor`, `colorVar`). Tokens `--branch-0…6` / `--branch-grey` in `index.css`.
- `src/lib/treeMap.ts` — tree map model: units (branches; end-of-line attempt stacks `stack:<fork key>`), tidy layout (`layoutTree`, port of the preview's `tidy()`), `currentUnit` (nearest drawn ancestor), `jumpSelection` (fork selections down to a unit). UI: `components/chat/TreeMap.tsx` (`TreeMapPanel` + SVG; hover growth via a mask animation).
- `src/lib/column.ts` — side-question column layout math (chat/column frame, pushed card tops, covered cards, marker lanes). UI: `components/side/SideColumn.tsx` (generic anchored items: measures highlight rects, cards, marker strip; notes plug in as another `kind`), `SideCard.tsx` (expanded thread card), `useSideQuestions.tsx` (side + note items, highlights per message, collapse rules), `useNotes.tsx` + `NoteCard.tsx` (notes). `src/lib/notes.ts` — note actions (create / save / archive / restore / delete) and titles.
- `src/lib/panes.ts` — side pane widths (defaults / limits); state in `useSettings().panes`; drag handle `components/ui/ResizeHandle.tsx` (our own: the right column isn't a flex panel a panel library could own — it lives in the chat's scroll area, placed by `columnFrame`).
- `src/lib/tree.ts` — tree navigation (active path, side-question threads, path to node; all skip archived nodes) and archive helpers (`isHidden`, `subtreeIds`, `busyIds`, `archivedItems`, `deriveBranches`).
- `src/components/layout/ArchiveDialog.tsx` — a conversation's archive (restore / delete forever).
- `src/lib/anchor.ts` — maps rendered Markdown ↔ source offsets: a rehype plugin wraps every text run with `data-s`/`data-e` (math and other unpositioned output become atomic ranges), highlights anchors (side questions `anchor-hl`, notes `anchor-note`), `remarkBreaksMapped` (remark-breaks that keeps positions, so user messages map too), and `rangeToSource` turns a DOM selection into source offsets.
- `src/lib/chat.ts` — conversation actions: send, stream, stop, build context messages.
- `src/lib/hooks.ts` `useAutoScroll` — the chat's and each side card's scrolling rules (follow the bottom, blank space instead of being pulled up — as bottom padding on `blankRef`, a wrapper inside the area: padding on the area itself made it taller and pushed the composer off screen —, `hold` + `ScrollHold` context to keep a clicked thing in place, a reset on conversation switch that keeps the view at the end while the messages load; see Product decisions › Scrolling). `MessageNode` marks its root `data-fork` (`atFork` in `useNodeActions`) and switcher `data-switcher` for holds.
- `components/chat/EditDialogs.tsx` — edit dialogs (user message with images, reply Markdown source). `components/detail/DetailDialog.tsx` — the request detail dialog.
- `src/lib/images.ts` — attachments: make a file sendable (`prepareImage`), store / load / prune images, mask base64 in recorded bodies. UI in `components/chat/Images.tsx` (`useAttachments`: button + paste + drop, thumbnails, viewer).
- `src/lib/naming.ts` — automatic titles for conversations and side questions (naming model, prompt, fallback titles).
- `src/lib/transfer.ts` — single-conversation export / import (JSON file, format below in Product decisions).
- `src/lib/params.ts` — per-model parameter configs: parse the user's JSON (`parseParamConfig`), apply choices + dependencies and merge bodies (`resolveParams`), custom header parsing. `paramsDoc.ts` is the user-facing format guide (zh/en, also meant to be pasted to an LLM).
- `src/lib/models.ts` — model list / per-model config edits (read-modify-write on the stored provider). `src/lib/presets.ts` + `presetData.ts` — built-in model presets (sources and open questions in `docs/presets-research.md`; `src/presets.test.ts` checks every preset parses and is sendable).
- `src/providers/` — one adapter per protocol (`ProtocolAdapter`: request building, `echo`, stream parsing, `aggregate`, model listing): `openaiChat`, `openaiResponses`, `anthropic`.
- `src/store/` — Zustand: `settings` (persisted to localStorage: lang, theme, last model) and `ui` (in-memory: current conversation, live streaming text, detail dialog, expanded side-question card, unsent side-question drafts, the main box's unsent text per conversation).
- Switching conversation goes only through `useUi().setConversation`; it clears the store's per-conversation UI (detail dialog, expanded card), and `ChatView` resets its own (tree map, overlap picker, hover links, pending jump) in the render where `conversationId` changes (no `useEffect`: that left a frame of the old state). The main `Composer` is keyed by conversation and starts from / saves to `composerDrafts`. Check with `scripts/browser/switch-suite.mjs`.
- `src/i18n/` — zh/en dictionaries; every UI string goes through `useT()`.
- `src/components/ui/` — shared primitives (Button, IconButton, Tip, HelpTip, Input, Label, Dialog, Menu, Segmented, `Layer`, `notifyError` toasts). Build new UI from these. `Layer` (Radix's `DismissableLayer`, same version as the one inside Radix's primitives — pnpm must resolve it to the same copy, or the stacks don't see each other) owns Escape / outside-click closing for anything that isn't a Dialog / Menu / Popover: only the topmost open layer (tree map, expanded card, menu, dialog, tooltip) gets Escape. Tooltips open on focus only when it came by Tab (a menu / dialog closed by Escape hands focus back to its button). Check with `scripts/browser/layers-suite.mjs` (how: its header).
- `src/lib/focus.ts` — where focus goes when what held it goes away (rules in its header): `Dialog` returns it to its opener (our dialogs have no Radix `Trigger`, so Radix dropped it on the page) or, after a send / save (`toComposer`), to that place's input box; retry, regenerate and opening a conversation focus the input box (`focusComposer`, finds `textarea[data-composer]`). Check with `scripts/browser/focus-suite.mjs`.
- `src/index.css` — design tokens as CSS variables (light + `.dark`). Components use semantic Tailwind colors (`bg-surface`, `text-muted`, `border-border`, `bg-accent`…), never raw palette colors.

## Data model

- `Conversation.selectedChild[parentId | ROOT_KEY]` remembers which child is shown at each fork.
- `ChatNode` = one user message + one assistant message + exactly one request `Attempt`.
  - `kind: 'main' | 'side'`. Side-question roots point `parentId` at the main node they were asked from and carry an `anchor` (offsets into the assistant content + the quoted source text; used for highlighting and locking only, never sent). Every side node has `thread` (one side question + follow-ups); retrying/editing a root makes another root with the same thread and anchor. The shown root version is remembered under `selectedChild[thread]` (see `forkKey`).
  - Node kinds (DB v5): main nodes carry `branch: true` or nothing (= attempt); side nodes never. Every new main node is an attempt; `sendMessage` sets `branch` on the main node a follow-up or side question is sent from; "设为分支" sets it by hand; never unset. DB v5 (and v1 imports) derive it: a main node with a main child or a side-question root is a branch (`deriveBranches`).
  - `archived` (timestamp) is set only on the node the user archived — for a side thread on every root version, same time; descendants stay unmarked and are hidden because an ancestor is archived (`isHidden` = node or anything above it archived). Restoring deletes the field.
  - `label` (main nodes, optional): the user's one-line label (`setLabel`; empty removes the field). Only shown in tips, never sent.
  - `assistant.content` is what's displayed and sent as context; `attempt.rawText` is the untouched model output. A node's reply never changes after streaming: editing makes a new sibling with `edit: { from, history, at }` (`history` = earlier versions oldest first, starting with the model's reply), no `assistant.reasoning`, and a **copy** of the source's `attempt`; `replyVersions()` lists its versions.
  - `Attempt` records the HTTP exchange verbatim: `requestHeaders` (**includes the API key** — owner's choice, so details show exactly what was sent; export strips it), `requestBody` (verbatim except image base64, replaced by `[image:<id>]`, so each request doesn't store another copy of every image in its context; exported files keep the marker and carry the images separately), `response` (status + CORS-readable headers), `rawChunks` (response body as received, with ms offsets). The detail dialog derives events / merged view from these; adapters provide `aggregate()` (generic delta merge, keeps unknown vendor fields).
- `Conversation.named` = title is final (named by the model or renamed by the user), automatic naming leaves it alone. `Conversation.threadTitles[thread]` = side-question titles from the naming model; threads without one show a fallback (first non-quote line of the root's text, else the anchored text).
- `user.images` = ids into the `images` table (DB v4: `StoredImage` with the Blob, mime, size; one per attachment, per conversation). Retries and edits that keep an image reuse its id; deleting a conversation deletes its images, deleting a side thread prunes unreferenced ones (`lib/images.ts`).
- `Note` (DB v6 `notes` table: `id, conversationId, nodeId`) = `{ nodeId, target: 'user' | 'assistant', anchor` (offsets into `user.text` / `assistant.content` + quoted text)`, text, createdAt, updatedAt, archived? }`. Main-line nodes only; never sent; stays on its node (retries / edits don't inherit it); hidden while its node is hidden. Empty notes are deleted (by the card, and at startup: `dropEmptyNotes`).
- Streaming text lives in `useUi().live[nodeId]` and is written to IndexedDB once at the end; `MessageNode` shows it only while the stored node is `streaming` and drops it once the stored node says it's over (dropping it at the write left a frame showing the empty stored reply). Nodes left `streaming` on reload are marked `aborted` at startup.
- The chat reads a conversation's data only through `useConversationData` (conversation + nodes + notes in one read transaction, `undefined` until they match the current id). Separate live queries resolved at different moments and mixed conversations / states for a frame (wrong path, dots, colors flashing on switch). Don't add other live queries for the open conversation's data.

## Product decisions

- Main view: linear chat of the active path. Turns are split by a thin separator; main-chat turns have a 3px bar in the left gutter in the turn's branch color (`lib/colors.ts`), its top 48px a gradient (in oklch) from the parent's color where that differs. Side threads get separators, no bar.
- Node labels (step 8.1b.2, owner 2026-10-08): "标注" in a main node's reply-footer ⋯ menu (first item) or a right-click on a node in the tree map (not on a stack) opens a prompt (prefilled; placeholder says where it shows and that empty removes it; Cancel keeps it). Shown first, bold, in the switcher dot tips and the tree map tips (a stack's tip lists its labelled attempts); the tree map reads labels live while its layout stays frozen. Nothing in the chat itself shows them (yet).
- Sibling switcher (`SiblingSwitcher.tsx`): right end of the reply footer of any node with ≥ 2 non-archived siblings — always visible, also while streaming (a row of its own), error replies included (the footer row under the error box; owner). Main nodes: one dot per branch in its color (oldest first, shown one ringed, tip = user message first line → reply first line, so same-text retries differ); then, after a divider, the attempts: a single attempt is one more grey dot; several are a grey stack — showing a branch, the stack is "×n" and jumps to the newest attempt; showing an attempt, the stack is ringed with ‹n/m› among the attempts. Side nodes: plain ‹n/m› over all versions.
- Tree map (`TreeMap.tsx`, step 6.3): header button (GitBranch, tip 树图) toggles a panel dropping down under the chat header over the chat (full column width, height = tree, ≤ 50vh, scrolls both ways). Drawn as in `docs/tree-preview.html` (GX 34, GY 22; bold hover mode, ≤ 0.3 s growth, shared prefix kept; tip = 第 N 轮 + user / reply first lines, stacks: 第 N 轮 · n 个尝试). Layout frozen while open. "当前" = topmost active-path turn (`data-turn`) still showing more than its footer when it opened, else nearest drawn ancestor / its stack. Click (or Enter on a focused node) = one `selectPath` write for every fork above it (stack → remembered attempt if in the stack, else newest), close, glide that turn to the top (`glideTo`: ≤ 250 ms, jumps most of a long distance first). Closes on Esc, outside click, the button, conversation switch, jump. A `HelpTip` in its top-right corner (outside the scrolling map) explains it: 左键跳转 / 悬停查看详细信息 / 右键标注 (owner, 2026-10-08).
- Retry / editing a user message → new sibling node, using the model currently selected in the picker (lets users compare models). Error boxes have no Retry button of their own (owner: the footer's regenerate and the one above the composer are enough).
- A turn that ended without reply text (failed, stopped before any text, reasoning only — `lacksReply`) can't be followed: its user message would go out unanswered. While it ends the path (main chat or a side card — confirmed), the composer's send is greyed out (typing still works) and a "重新生成" button sits centered right above the box (same as the footer's). A reply cut off with partial text is a normal turn. (Owner's choice.)
- Editing an assistant message → a new sibling version (same fork / thread / anchor), shown at once; the original stays untouched with its reasoning, follow-ups and side questions. The edited version has no reasoning (not shown, never echoed — `echoFields` skips `node.edit`), no follow-ups or side questions of its own yet, and shows its source's request/response in details with a note and a "查看原回复" button. Editing an edited version makes another sibling whose history extends the chain. (Owner's decision. Why: overwriting has unsolvable edge cases — encrypted reasoning / signature checks, edit-then-revert leaving two heavily overlapping reasoning chains — and an overwrite can change the meaning so it contradicts the reasoning; one simple rule also keeps users from getting lost or looking up rules. Accepted cost: in a long conversation you can't fix an early mistake in place.)
- Request detail = a dialog (`useUi().panel`, `DetailDialog`; owner: dialogs leave far fewer layout cases than the old docked panel): ⓘ in the reply footer, "详情" on error boxes, main chat and side cards alike. Nothing behind it moves; Escape / outside click closes it (an expanded side card stays). "查看原回复" switches the chat behind it and shows that node's detail. Switching conversation closes it.
- Editing a user message or a reply happens in a dialog (`EditDialogs.tsx`; owner). Closing it with changes asks first (Esc / outside click / ✕ / Cancel). After sending / saving, the new node's top takes the old node's place on screen (owner: "the new node's message top = the current node's message top"); the same for retry.
- Scrolling (owner, step 7) — one set of rules, all in `useAutoScroll` (the chat, and each side card's message area); don't add scroll adjustments elsewhere:
  1. The view moves on its own only while *following* (keeping the end of the messages in view as they grow); anything else that changes size leaves what's on screen where it is.
  2. Following turns on when the user sends or retries / edits, on switching conversation and when the user scrolls to the end; it turns off when the user scrolls away from the end, clicks a reasoning toggle / the switcher (they're reading what's on screen; otherwise the view jumped to the end once the hold ended — owner found this) or drags out a text selection in the area (borrowed from `use-stick-to-bottom`; owner agreed: following pulled the text from under the mouse). Nothing else changes it (content getting shorter doesn't). Only a press on the scrollbar counts as scrolling, not clicks on the content.
  3. Never pulled up: where content got shorter at the end, blank space is added at the bottom instead; trimmed away unnoticed.
  4. What the user clicks stays put for a moment (`hold`): reasoning toggle, version switcher, the passage a side question / note is created from (the column may appear and narrow the chat — the text rewraps; following was still on after the reply and scrolled it away), a retry / edit (the new node's top where the old one's was, at least at the top; its reply is then followed only until that top reaches the top of the screen). Scrolling by hand ends it at once.
  Why: the first version (step 7) had several independent mechanisms (follow, holds, blank, card reveal, auto-folding reasoning) that set off each other while streaming; the owner found jumps. Run `scripts/browser/scroll-suite.mjs` (how: its header) after any change touching scrolling, streaming display, reasoning or side cards; it checks following, selecting while following, scrolled up while thinking, unfolding while following, unfolding after a retry with blank below, new conversation / switching back, unfolded reasoning crossing the top, folding from the stuck toggle, retry, switching, the side card (page still, card still, fixed height, follows) and the note card (fits on screen, fixed height, typing / 完成 / collapsing move nothing).
- Reasoning: folded by default and opened / closed only by the user, also while it streams — never automatically (owner). No inner scroll box — unfolded it shows in full; while it runs past the top of the screen its "思考过程" toggle sticks to the top of the scroll area (main chat or side card), so it can be folded from there, and folding keeps it at the top with the reply right below (owner).
- Side questions: select text in a main-line assistant reply (body only, not reasoning or user messages) → floating "追问" → a draft card expanded in the side-question column at the selection. The input box is prefilled with the selection as a `> ` blockquote + blank line, so the user decides what gets quoted; context = root→node main path + the side thread, sent as typed. Side threads never enter the main context. A thread is a full mini-chat (follow-ups, retry, edit, ‹n/m›). No side questions inside side answers. Anchored text is highlighted; click expands its card, overlapping highlights show a picker. The expanded card's ⋯ menu (owner, 2026-10-08): 重命名 (sets `threadTitles[thread]`; shown at once even while a naming request runs, which then leaves it alone) and 归档 (the whole thread; no confirm: reversible); drafts have no menu. Clicking an expanded card's header (not its buttons) collapses it — side and note cards alike (`collapseOnClick`); they have no collapse button (owner removed it; Escape and the header do it; scripts: `collapseCard` in lib.mjs).
- Side-question column (`useUi().expanded` / `drafts`): right of the chat inside its scroll area, always there (open or collapsed to its marker strip, see the next point). Width depends only on the window and the user's dragged width (`sideWidth` + `columnFrame`: chat stays centered while the column fits, else shifts left, then narrows; column 260–640 px, default 380, never leaving the chat under 420 px). Collapsed card = title (naming dots) + the same ⋯ menu as its expanded card, shown on hover (`CardMenu.tsx`; owner, 2026-10-08: the turn count / "笔记" on the right went; drafts keep a small "草稿" and have no menu), top = its anchor's first line, pushed down only to avoid overlap; positions follow content resizes (0.2 s transition). One expanded card at its anchor covers the cards it overlaps (they fade out, bars stay). Every expanded card has a fixed height (min(75vh, scroll area − 32 px)): a side question's messages scroll inside with the same rules as the chat, a note's text / editor scrolls inside (owner, 2026-10-07: notes used to be as tall as their text — they then hung off the bottom of the screen, typing pushed the chat up, and 完成 / collapsing made it jump). Expanding never scrolls the page (owner); a card that wouldn't fit on screen below its anchor opens shifted up by just enough, fixed once open (confirmed by the owner after trying it; rejected: choosing only between opening down or up from the anchor — at 75vh a card then often overhangs the screen when its anchor is mid-screen, and a half-screen card was too small). Marker strip: a bar per anchor (lines it spans; overlapping anchors in side-by-side lanes), tip = title · turns, click = expand; hovering a card / bar deepens its highlight and vice versa. Escape collapses (not while focus is in an input / menu / dialog — except the card's own input box with nothing typed: empty or still just the prefilled quote; `data-pristine` on the composer). Drafts: an empty one (nothing beyond the prefilled quote) vanishes when its card closes; a typed one stays as a "草稿" card (text + images kept in memory per conversation); the first send makes it a thread. A card whose thread leaves the path (archived, other branch) collapses; switching conversation collapses.
- Collapsible, resizable side panes (owner, 2026-10-07; step 8.1a): both the conversation list (left) and the side-question column (right) collapse and expand **only through their header buttons**, and their width is dragged at their inner edge. Open / closed and widths are global (`useSettings`, persisted), unaffected by switching conversation. The right column, when open, takes its space even with nothing in it (owner: "可以空展"); collapsed it leaves only the marker strip and the chat recenters. Clicking a highlight or a bar toggles its card (expanded → collapses, else expands); with the column collapsed, that click (and creating a side question / note) opens the column and the card — opening only, never closing it. Left collapsed: the chat header shows expand + new chat buttons. Right: its button is at the header's right end (after the tree map's); its drag handle sits over the column's left edge, the scroll area's height. Opening / closing slides (0.2 s; the list keeps its width and is clipped; the chat, input box and column move together — CSS transitions switched on only for the slide, not while dragging or resizing the window). Widths: list 200–420 (default 256); double-click a handle = default. (Owner found a one-frame jump on toggling: the chat was re-laid out a frame late — `ChatView` now re-lays out in the same frame, `flushSync`; `layout-suite` W4 / W5 check every frame.)
- Input box floats (owner asked 2026-10-07: no background-colored bottom strip cutting off the chat and the column; owner tried it 2026-10-08, accepted): the chat's scroll area and the side column reach the window's bottom; the main input box is laid over the chat's bottom (`data-main-composer`, absolute; the strip around it lets clicks through), the chat column's width less 12 px a side (messages: less 24 px), 16 px above the bottom, `z-10` (the sticky reasoning toggle has a z-index and showed over the box — owner). Below the box and beside its lower half the background covers the messages (owner: text needn't show under it); only above that do they pass visibly. (Scripts: Playwright's `hover()` scrolls its target out from under the box; use `hoverAt` in lib.mjs.) The messages end above it: a spacer after them as tall as the box (an element, not padding — `useAutoScroll` observes the content box, and padding growth went unseen, so a growing box covered the reply; `scroll-suite` IB).
- Notes (step 6.5): selecting text in a main-line reply body or user message → the floating pill has "笔记" (replies: "追问 | 笔记"; user messages: only "笔记"). Creates an empty note and expands its card straight into editing. Same column as side questions (same stacking, one-expanded rule, covering, bars, hover links, click-to-expand, overlap picker listing both kinds). Note style = amber (`--c-note*` highlights, `--c-mark-note*` bars, amber NotebookPen icon); collapsed card = icon + first line (Markdown markers dropped, muted) + ⋯ on hover; bar tip = first lines. Overlapping side question + note = indigo tint with both underlines. Expanded card: header (icon + 笔记, ⋯ menu with 归档 — no confirm, shown once it has text; a click on it collapses the card), rendered Markdown (`prose-compact`) + "编辑"; editing = autosizing textarea (local state, saved 400 ms after typing stops and on leaving) + hint "笔记只给自己看…" + "完成"; Escape in the editor = 完成, otherwise collapses. A note empty when its editor closes or its card goes away is deleted outright.
- Editing an assistant reply: plain Markdown source editor in a dialog (no locks — the original keeps its anchors). Also offered on a reply without text (failed, stopped early): the user writes one, saved as a new version like any edit (owner agreed); the version history then shows the original as "（没有回复正文）". The "历史版本" tab of the detail dialog exists only on edited versions; its versions show in full (no inner scroll box).
- Protocols: OpenAI Chat Completions (base URL incl. `/v1`, → `/chat/completions`), OpenAI Responses (→ `/responses`), Anthropic Messages (base URL **without** `/v1`, as in Anthropic's SDKs, → `/v1/messages`; sends `x-api-key`, `anthropic-version`, `anthropic-dangerous-direct-browser-access`). Settings show the resulting request URL. No check for fields an API requires (e.g. Anthropic `max_tokens`): the API's own error shows in the chat (owner's choice: other vendors now speak the Anthropic protocol too, such rules won't last).
- Native replies: anthropic keeps the message with its content blocks; responses keeps `{ output }` (reasoning + message items). Echo per protocol (`adapter.echo`): anthropic puts echoed thinking/redacted_thinking blocks before the text block; responses puts reasoning items before the native message item (id kept, text replaced by `assistant.content`). Replies recorded under another protocol (provider switched) are never echoed.
- Providers: **no defaults.** "Add provider" makes a blank form. The app adapts per *protocol*, never per vendor, and adds no optional request fields itself (not even `stream_options`); the request body is only the protocol's required fields + the model's parameter config.
- Models: settings show the provider's models as a list (no text box). Clicking a row (anywhere but its delete ✕) or its gear opens that model's config dialog; "添加模型" opens the same dialog for a new model. The dialog edits a draft: Cancel (asks if changed) / Save; nothing is validated while typing, Save checks name, parameter JSON and header lines and lists every problem in one error notification. "从接口获取" adds new names, never removes; if the deduplicated list has ≥ 12 models (`PICK_THRESHOLD`) it instead opens a dialog listing them all (search, an add button per row; already-added ones greyed). Everything per model lives in `Provider.modelConfigs[model]` (`ModelConfig`: `params`, `echoReasoning`, `echoFields`, `headers`, `preset`); DB v3 migrated the old provider-wide fields into every model.
- Presets: built-in, per protocol + model + channel (currently only vendors' official APIs). The config page's top card opens a picker listing every preset; its only tags are channel ("官方"), model family (DeepSeek / GPT / Claude) and protocol (no descriptive tags — owner's choice), filterable as chips (any within a group, all groups). Presets for another protocol than the provider's are greyed out and can't be picked. A preset holds only a model config (params, echo, headers) — no model id, no base URL (owner's choice: third-party channels may serve a model with the official parameter config, so a preset must be usable there too). Applying one **replaces** the model's whole config (confirm if it had any) and never touches the model name or the provider. Presets offer no temperature control (owner's choice: fading out, rules too vendor-specific). The page notes whether the config still matches the preset. "Copy from another model" copies a whole config the same way.
- Model parameters (`ModelConfig.params`, JSON text in the format of `lib/params.ts` / `paramsDoc.ts`): per model. Four types — `choice` (placeholder `"EFFORT"`), `range` (placeholder `"VALUE"`, min/max/step), `fixed`, `silent` (always sent, not shown). The first three have a name, optional `toggle` (+`defaultOn`), `default`, and `requires` (`{name: true|false|value|[values]}`; chains allowed, cycles rejected). Switch semantics (owner's): a switch = optional (any param with `requires` always gets one); usable switch = no dependency restricts it; greyed switch (shown off) = unmet dependency, can't be sent, and the user's position returns once it's met; on = sent and its value control shown; off = not sent, value control hidden; no switch = always sent. Bodies deep-merge in config order; the protocol's own fields (`adapter.reserved`) are rejected. Parse errors are reported when the model config is saved, so a stored config is always valid (no UI for an invalid stored one; old data needn't be handled during development — owner). "Copy from another model" exists; a format guide dialog has a copy button.
- The model picker and parameter controls live in the composer's bottom bar (main and side panel share them). Parameter choices are remembered per provider+model in `useSettings().paramChoices`.
- Echo-back ("回传思维链", `ModelConfig.echoReasoning`; the *target* model's setting decides) and custom headers (`ModelConfig.headers`, `Name: value` lines, may replace built-ins case-insensitively; model listing sends none) are separate from parameters. Echo on with no `echoFields` → automatic: the first field present from the adapter's `echoPriority` (openai-chat: `reasoning_details` › `reasoning_content` › `reasoning`; only one, since they duplicate each other). Anthropic: all thinking + redacted_thinking blocks (one reasoning); Responses: reasoning items. Manual `echoFields` mean field names / block types / item types respectively.
- Reasoning / encrypted reasoning: `attempt.message` holds the reply in native protocol shape (unknown fields included). `ModelConfig.echoReasoning` / `echoFields` pick which of its fields are sent back in context (see above; `*` = all); only to the **same provider** that produced the reply (stricter than same-protocol: another vendor's encrypted blobs/signatures are useless or rejected). Text always comes from `assistant.content`. Display (`lib/reasoning.ts`) recognizes `reasoning_content` / `reasoning`, OpenRouter `reasoning_details` (text / summary / encrypted → lock badge), Anthropic `thinking` / `redacted_thinking`, Responses `reasoning` items (summary parts, `reasoning_text`, `encrypted_content`), and leading `<think>` blocks (moved out of `assistant.content`; raw stays in `rawText`). In request details, history reasoning folds with history messages.
- Automatic naming: optional "命名模型" in Settings › General (`useSettings().namingModel`, any provider's model, sent with that model's parameter config; a "参数调节" button next to the picker sets choices used only for naming, remembered under `namingParamKey` apart from the chat choices; off = first line of the message as title, as before). A conversation is named from its first message + reply, once that reply finishes successfully; a side question from up to two main-line turns above where it was asked (as background) plus its root message + reply. Prompt = Chatbox's `nameConversation` (adapted wording for side questions), UI language, each message cut to 200 chars. While the reply or the naming request runs, the title spot (sidebar, chat header, side panel header) shows bouncing dots. Failure (or the chosen naming model was deleted) → error notification and the first-line fallback (confirmed by the owner, accepting that it repeats for every new conversation while the naming model is broken). The 200-char cut (Chatbox: 100, too short for a quoted side question) and titles in the UI language are confirmed too. The side panel header shows the thread title with a small "侧边提问" below (no icon).
- User messages and notes render as Markdown too, with single newlines kept as line breaks (`remark-breaks`; notes: owner, 2026-10-07).
- Images in user input (main chat, side questions, editing a user message): attach button, paste (only when the clipboard has no plain text, so copied spreadsheet cells still paste as text), or drop — onto the whole chat column / side panel, or onto the message editor. Shown as thumbnails above the user bubble (click → full-size viewer). Sent before the text in each protocol's native shape (openai-chat `image_url` data URL, Responses `input_image`, Anthropic base64 `image` block); an image-only message has no text part; messages without images stay plain strings. Images are kept byte for byte when PNG/JPEG/GIF/WebP ≤ 5 MB and ≤ 8000 px a side (Anthropic's limits, the strictest); otherwise converted to PNG or downscaled JPEG. No per-model "supports images" check — a model that can't see images returns the API's error.
- Unsent text (and images) in the main input box stays with its conversation (owner, 2026-10-07): switching shows that conversation's own unsent text; the not-yet-created new chat has its own; in memory only, like side-question drafts (gone on reload). It used to carry over into the next conversation, where Enter sent it to the wrong one.
- No tool calling.
- Archive (step 6.1) replaces every node deletion except deleting a whole conversation. Main-line reply footer ⋯ menu: "设为分支" (attempts only) and "归档"; side nodes have no menu (a side thread is archived as a whole from its panel). Archiving is disabled while the node or anything below it is streaming (tip says why); archiving what the right panel shows (or something above it) closes the panel. Tree helpers skip archived nodes; if the remembered child at a fork is archived, the newest remaining child shows; if none remains, the path ends there. Archiving leaves the remembered selection alone; restoring first pins what's shown at that fork, so restoring never switches the view. Conversation ⋯ menu → "查看归档" opens the archive dialog: entries newest first (archived main node, or a whole side thread), each with kind (尝试 / 分支 / 侧边提问), first line (side: thread title or fallback), where it sits ("在第 N 轮「…」之后" / "问自第 N 轮「…」" / "在对话开头"), node count (`subtreeIds`, side nodes included), archive time, Restore and Delete. Restore is disabled (with a tip) while anything above it is archived. Notes are entries too (kind 笔记, first line, "在第 N 轮「…」的回复上 / 的提问上", no node count; Restore blocked while their node is hidden; Delete removes just the note). Delete (danger confirm) deletes the entry's whole subtree (archived or not, side threads included), the notes on it, its `selectedChild` / `threadTitles` entries, and prunes unreferenced images.
- Export / import: one conversation at a time, as a JSON backup only (no Markdown — owner's choice). "导出" in a conversation's ⋯ menu; import button next to "新对话". The file (`format: "explore-with-llm/conversation"`, `version: 4`; nodes carry `branch` / `archived` / `label` as stored; `notes` = all its notes, archived included) has the conversation, **every** node (all branches, side threads, edited versions) with the full raw request records, and its images as base64. API keys are removed: credential-like header values become `[removed]`, and any known provider key or credential header value is scrubbed from every string. Import accepts versions 1–4 (v1: `branch` derived like DB v5; v1/v2 have no notes; v1–v3 no labels), validates the file (incl. `branch` / `archived` / `label` types and note shape), gives every id (conversation, nodes, threads, images, notes, `[image:<id>]` markers) a new one so importing twice makes two copies, marks `streaming` nodes `aborted`, sets `updatedAt` to now and opens it. `providerId` is kept, so echo-back works only if that provider exists in this browser.
- Errors (owner's rules): a failed action the user just took (import, unreadable image, model fetch, saving a model config) → error notification (`notifyError`, top right, stays until closed). A chat request's errors stay in the chat as the red error box with Details (HTTP errors, stream error events, `network`, `interrupted` = connection dropped mid-reply with the partial text kept, empty reply). No request timeout (reasoning models can think for minutes); before the first output the reply shows "已等待 N 秒" after 5 s. A standing problem the user isn't looking at (e.g. the naming model was deleted) → one error notification when it matters (here: when a title was due); an identical notification already open isn't shown again (owner: notifications stay until closed, so once is enough). Every error message names what it is about (e.g. each save problem is prefixed with its field: "自定义请求头：第 1 行…").
- Success feedback: so far always a brief in-place confirmation (the button turns into ✓ + text for ~1.5 s, like copy buttons and "✓ 获取成功") or simply the visible result (dialog closes, list updates, conversation opens). Whether some future case should show a success notification is undecided (owner) — ask when one comes up.
- Help texts: consequences the user needs while deciding stay visible (request URL preview, "API Key 只保存在浏览器", edit-mode notes, state notes in the detail dialog); explanations of how something works go behind a hover question mark (`HelpTip`, `Label help=`; a click pins it open until the next click on it, a click elsewhere or Escape); anything the UI already makes obvious is removed. Tooltips are always the app's `Tip`, never a native `title`.
- UI languages: zh + en. Desktop only.
- UI should be clean and polished but not complex.

## Engineering principles

- Before writing anything general-purpose, look for a mature library (installed ones first, e.g. Radix for overlays). Write our own only where nothing fits, and say why here. (Owner: "borrow predecessors' wisdom, don't reinvent wheels".)
- One owner per shared concern (data reads: `useConversationData`; scrolling: `useAutoScroll`; Escape / outside clicks: `Layer` + Radix primitives; focus: `lib/focus.ts` + `Dialog`). No second mechanism beside it.
- Derive, don't store a second copy (colors are computed from the tree; the streamed-text race came from two copies of the same text).
- Tests guard the rules of these foundations (e.g. the scroll suite), not one test per reported bug.
