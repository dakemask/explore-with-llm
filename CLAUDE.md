# Explore with LLM

Pure-frontend branching chat app. Users bring their own provider + API key; all data lives in the browser (IndexedDB). Deployed as a static site to GitHub Pages (`.github/workflows/deploy.yml`). No backend, no proxy.

The owner is not a programmer. Claude decides *how* things are built (code, libraries, architecture); the owner decides *what* users see and do. A technical choice that changes behavior the user notices, costs, or is hard to undo is explained in plain words and put to the owner (see Engineering principles › Before building). Requirements are disclosed incrementally — record each new decision in "Product decisions".

## Way of working

- There is a list of tasks (see Tasks; mostly independent, some depend on others). The owner and Claude pick one, and tasks can be added at any time.
- When a task is built and checked (see Verifying changes), update Tasks (status: built, owner to try) and commit; the owner tries it in the browser; then it's accepted and its rules move into Product decisions (with why, and who decided).
- One task at a time, the owner trying it before the next, even with subagents. Briefs for anything touching a shared concern must say "only through its owner" and include scenarios where features act together (streaming + switching + cards). Review in motion, not just screenshots. Before a big feature, walk through failure / empty / streaming / Escape cases with the owner. (Owner's lessons from step 6.)

## Commands

- `pnpm dev` — dev server
- `pnpm test` — unit tests (vitest)
- `pnpm build` — typecheck + production build into `dist/`
- `pnpm mock` — fake streaming server on :8787 speaking all three protocols, picked by path (see `scripts/mock/server.mjs`; `EXTRA_MODELS=20` lists filler models, for the ≥ 12 picker)

## Verifying changes

The owner can't review code, so check changes in a real browser before reporting done:
run `pnpm dev` + `pnpm mock`, then drive the page with `playwright-core` using the locally installed
Chrome (`C:/Program Files/Google/Chrome/Application/chrome.exe`) — install playwright-core in the
session scratchpad, not in this project. Add a provider of any protocol with base URL `http://localhost:8787`;
model `mock-chat` streams plain reasoning + markdown/code/math, `mock-think` streams summary + encrypted reasoning (OpenRouter `reasoning_details` / Anthropic `redacted_thinking` / Responses two summary parts + `encrypted_content`), `mock-tags` puts `<think>` in the content, `mock-bad` returns 401, `mock-cut` drops the connection mid-reply, `mock-empty` streams nothing, `mock-hang` never answers, `mock-name` replies with a short title naming the prompt it got (conversation / side question + context message count), `mock-long` = mock-chat with 40 paragraphs of reasoning (a line every 120 ms, ~5 s) and the reply three times (scroll / sticky tests); Anthropic requests without `max_tokens` get a 400. Every reply starts with a line echoing the request counter, protocol, context size, reasoning echoed back in the context, body fields beyond the protocol's own (i.e. the model's parameters), the number of images in the whole context, and the last user message; image parts of the wrong shape get a 400.

Regression suites live in `scripts/browser/*-suite.mjs` (`scroll`, `layers`, `selection`, `focus`, `switch`, `layout`; what each guards: its header); `run-all.mjs` there runs them side by side and starts / stops the mock itself (all six ≈ 3 min, bounded by the scroll suite, vs ≈ 5.5 min one after another).

How much to check depends on whether a change touches a shared concern, not on how big it looks (owner, 2026-10-08: full checks for tiny tasks were too slow; the foundations now make small additions predictable). The level comes from the same assessment as Engineering principles › Before building:
- Always `pnpm test` + `pnpm build` (unit tests were once left broken because only the browser suites were rerun).
- **Small** — text, i18n, tip contents, icons; styles or logic inside one component that touches no shared concern: just that; if it looks different, one cropped screenshot of that spot, one theme.
- **Medium** — a new small component / menu item built on the existing owners (`Layer`, `Dialog`, `focus.ts`, `useAutoScroll`…) without changing them: + the suite of the concern it uses (e.g. a menu → `layers-suite`).
- **Large** — changes a shared concern's owner (`useAutoScroll`, `Layer`, `focus.ts`, `ChatView`'s switch reset, `column.ts`, `useConversationData`), the data model / export format, streaming, or a feature spanning several parts: the full check (all suites, the browser in motion, both themes when styles change). Anything touching scrolling, streaming display, reasoning or side cards runs `scroll-suite`; extend it with every scroll bug the owner reports.
- Before marking a task "built, owner to try", run the full `run-all.mjs` once, so small changes that add up are still checked together.
- Screenshots only for new looks, cropped to the changed area; skip them where a suite already asserts the numbers (positions, widths, jumps). Both themes only when colors / tokens change.

Shortcuts for scripts: seed the provider by writing straight into the `providers` store of the
`explore-with-llm` IndexedDB and reloading (faster than clicking through Settings; raw IndexedDB writes
aren't seen by Dexie live queries until a reload). To wait for a
reply to finish, wait for the Stop button (`aria-label="停止"`) to disappear — the Send button exists
(disabled) even while streaming. To attach an image, make the PNG in the page (`canvas.toDataURL`) and
`setInputFiles` it on `input[accept="image/*"]`; hand-written PNG bytes are easily invalid and silently rejected.
Playwright's `click()` / `hover()` scroll their target into view first, which spoils scroll-position checks:
place things with `scrollTop`, then click with `page.mouse` at the element's box (`hoverAt` / `clickAt` in
lib.mjs; `hover()` also scrolls targets out from under the floating input box). A programmatic scroll within
1.2 s of a fold / switch / retry is undone by the scroll hold (`useAutoScroll`); wait before scrolling in scripts.
To select text by mouse drag, press on a line (e.g. the box's top + 12 px), not the vertical middle of a
multi-line paragraph — that can land between lines and select nothing (no pill appears). Cards have no collapse
button: collapse them with `collapseCard` (lib.mjs, clicks the header).

## Gotchas

- Git Bash heredocs on this machine can eat backslashes. Write files containing `\` (LaTeX, regex) with the Write tool, not heredocs. Long multi-edit Python heredocs also tend to fail to parse; use Write/Edit. Heredocs also mangle non-ASCII (Chinese) text; for scripted multi-edits, write the `.py` to the scratchpad with the Write tool and run it with `PYTHONUTF8=1`.
- Python's `open(..., 'w')` on Windows writes CRLF; the repo is LF (`.gitattributes`). Pass `newline='\n'`.
- Tailwind v4 `translate-*` utilities use the CSS `translate` property, which stacks with `transform` in keyframes. Animations on centered elements must not use `translate()` in `transform`.
- Radix Dialog autofocuses the first button, which opens its tooltip. `Dialog` focuses the panel instead (`onOpenAutoFocus`); keep that for new dialogs.
- Inputs bound to Dexie data must keep local state (IndexedDB writes are async; binding directly drops keystrokes). See `ProviderForm`.
- Anything animating past the viewport edge (e.g. the panel's slide-in) makes Windows Chrome flash a scrollbar and jump the page; the app root has `overflow-hidden` for this — keep it. Headless tests use overlay scrollbars, so check `document.documentElement.scrollWidth` instead of eyeballing.
- Streaming mock replies can finish before a test clicks Stop; run `DELAY=60 pnpm mock` for stop tests.
- Headless Chrome hides scrollbars (overlay-like): pass `open({ scrollbars: true })` (lib.mjs) to see Windows' classic ones, which take width. A position read in `requestAnimationFrame` can be from before our ResizeObserver fix in that frame (not what's painted): to check painted frames, also read in a ResizeObserver created after the app's (see `layout-suite` W3).
- The project has no formatter config; don't run `npx prettier` (its defaults reformat whole files). Match the surrounding style by hand.

## Data model

- `Conversation.selectedChild[parentId | ROOT_KEY]` remembers which child is shown at each fork.
- `ChatNode` = one user message + one assistant message + exactly one request `Attempt`.
  - `kind: 'main' | 'side'`. Side-question roots point `parentId` at the main node they were asked from and carry an `anchor` (offsets into the assistant content + the quoted source text; used for highlighting only, never sent). Every side node has `thread` (one side question + follow-ups); retrying/editing a root makes another root with the same thread and anchor. The shown root version is remembered under `selectedChild[thread]` (see `forkKey`).
  - Node kinds (DB v5): main nodes carry `branch: true` or nothing (= attempt); side nodes never. Every new main node is an attempt; `sendMessage` sets `branch` on the main node a follow-up or side question is sent from; "设为分支" sets it by hand; never unset. DB v5 (and v1 imports) derive it: a main node with a main child or a side-question root is a branch (`deriveBranches`).
  - `archived` (timestamp) is set only on the node the user archived — for a side thread on every root version, same time; descendants stay unmarked and are hidden because an ancestor is archived (`isHidden` = node or anything above it archived). Restoring deletes the field.
  - `label` (main nodes, optional): the user's one-line label (`setLabel`; empty removes the field). Only shown in tips, never sent.
  - `assistant.content` is what's displayed and sent as context; `attempt.rawText` is the untouched model output. A node's reply never changes after streaming: editing makes a new sibling with `edit: { from, history, at }` (`history` = earlier versions oldest first, starting with the model's reply), no `assistant.reasoning`, and a **copy** of the source's `attempt`; `replyVersions()` lists its versions. Echo skips edited nodes (`node.edit`).
  - `Attempt` records the HTTP exchange verbatim: `requestHeaders` (**includes the API key** — owner's choice, so details show exactly what was sent; export strips it), `requestBody` (verbatim except image base64, replaced by `[image:<id>]`, so each request doesn't store another copy of every image in its context; exported files keep the marker and carry the images separately), `response` (status + CORS-readable headers), `rawChunks` (response body as received, with ms offsets). `attempt.message` = the reply in native protocol shape (unknown fields included; anthropic: the message with its content blocks; responses: `{ output }`). The detail dialog derives events / merged view from these; adapters provide `aggregate()` (generic delta merge, keeps unknown vendor fields).
- `Conversation.named` = title is final (named by the model or renamed by the user), automatic naming leaves it alone. `Conversation.threadTitles[thread]` = side-question titles (from the naming model or renamed by the user); threads without one show a fallback (first non-quote line of the root's text, else the anchored text).
- `user.images` = ids into the `images` table (DB v4: `StoredImage` with the Blob, mime, size; one per attachment, per conversation). Retries and edits that keep an image reuse its id; deleting a conversation deletes its images, deleting a side thread prunes unreferenced ones (`lib/images.ts`).
- `Note` (DB v6 `notes` table: `id, conversationId, nodeId`) = `{ nodeId, target: 'user' | 'assistant', anchor` (offsets into `user.text` / `assistant.content` + quoted text)`, text, createdAt, updatedAt, archived? }`. Main-line nodes only; never sent; stays on its node (retries / edits don't inherit it); hidden while its node is hidden. Empty notes are deleted (by the card, and at startup: `dropEmptyNotes`).
- `Provider.modelConfigs[model]` = everything per model (`ModelConfig`: `params`, `echoReasoning`, `echoFields`, `headers`, `preset`); DB v3 migrated the old provider-wide fields into every model.
- Streaming text lives in `useUi().live[nodeId]` and is written to IndexedDB once at the end; `MessageNode` shows it only while the stored node is `streaming` and drops it once the stored node says it's over (dropping it at the write left a frame showing the empty stored reply). Nodes left `streaming` on reload are marked `aborted` at startup.
- The chat reads a conversation's data only through `useConversationData` (conversation + nodes + notes in one read transaction, `undefined` until they match the current id). Separate live queries resolved at different moments and mixed conversations / states for a frame (wrong path, dots, colors flashing on switch). Don't add other live queries for the open conversation's data.

## Product decisions

What users see and can do, and why. These rules are deliberate: don't change one without the owner, and write the new rule and its reason back here. Unmarked rules were decided by the owner or accepted by the owner after trying them; "(Claude, unconfirmed)" marks choices the owner hasn't confirmed yet. Implementation notes live in Architecture.

### Concepts (owner; names 尝试 / 分支 / 归档 not final)

- A main node's children are *attempts*, *branches*, *archived* nodes and side questions. Every new node (send, retry, edit user message, edit reply) is an attempt of its parent; an attempt that gets a follow-up or a side question becomes a branch; attempts can be made branches by hand ("设为分支"), never back.
- Attempts and branches can be archived (with their subtree) and restored to their former kind. Deleting happens only inside the archive (it deletes the subtree), apart from deleting a whole conversation. One archive per conversation.

### Main view, colors and navigation

- Main view: linear chat of the active path. Turns are split by a thin separator; main-chat turns have a 3px bar in the left gutter in the turn's branch color, its top 48px a gradient (oklch) from the parent's color where that differs. Side threads get separators, no bar.
- Colors ("rainbow flow"): 7 colors on a ring (red, orange, yellow, green, cyan, blue, violet; yellow-green dropped as too close), each at its own lightness. A segment runs from one fork to the next; a fork = ≥ 2 branches (one branch + attempts is not a fork, the branch keeps the color). At a fork the branches take the next colors along the ring in creation order (first = parent + 1, …), so colors change only below forks — accepting that a line's lower part recolors when a second branch appears. Attempts are always grey, a lone one too (owner, 2026-10-07: the parent's color made a fresh reply look settled). Rejected: equal-lightness 8-color jump, hue-interval splitting.
- Sibling switcher: right end of the reply footer of any node with ≥ 2 non-archived siblings — always visible, also while streaming (a row of its own), error replies included (the footer row under the error box). Main nodes: one dot per branch in its color (oldest first, the shown one ringed; tip = the node's label in bold if it has one, then user message first line → reply first line, so same-text retries differ); then, after a divider, the attempts: a single attempt is one more grey dot; several are a grey stack — showing a branch, the stack is "×n" and jumps to the newest attempt; showing an attempt, the stack is ringed with ‹n/m› among the attempts. Side nodes: plain ‹n/m› over all versions.
- Tree map: header button (GitBranch, tip 树图) toggles a panel dropping down under the chat header over the chat (full column width, height = tree, ≤ 50vh, scrolls both ways).
  - Horizontal tidy tree, frozen while open (no relayout on click). Only end-of-line attempt stacks are drawn (grey circle, ×n); attempts beside branches are not. The current turn has a black ring + "当前" label (no pulse) and the map opens scrolled to it.
  - Hover: the root→node path gets thicker lines and 1.2× dots, growing from the root in ≤ 0.3 s, shared prefix not redrawn. Tip = label (bold, if any) + 第 N 轮 + user / reply first lines; stacks: 第 N 轮 · n 个尝试 + their labelled attempts. Labels are read live while the layout stays frozen.
  - Click (or Enter on a focused node) jumps there: every fork above it switches at once (a stack → its remembered attempt if in the stack, else the newest), the map closes, that turn glides to the top. Right-click a node (not a stack) = 标注.
  - Closes on Esc, outside click, the button, conversation switch, jump. A help tip in its top-right corner (outside the scrolling map): 左键跳转 / 悬停查看详细信息 / 右键标注 (owner, 2026-10-08).
  - Rejected: straightening the selected path, dimming the rest, rings, highlighter band, casing, dotted trail.
- Node labels: "标注" (first item of a main node's reply-footer ⋯ menu, or right-click in the tree map) opens a prompt (prefilled; the placeholder says where labels show and that empty removes it; Cancel keeps it). Shown only in the switcher dot tips and tree map tips; nothing in the chat itself shows them (yet). No right-click menu in the chat body (it would take the browser's own).

### Branching and editing

- Retry / editing a user message → new sibling node, using the model currently selected in the picker (lets users compare models). Error boxes have no Retry button of their own: the footer's regenerate and the one above the composer are enough.
- A turn that ended without reply text (failed, stopped before any text, reasoning only) can't be followed: its user message would go out unanswered. While it ends the path (main chat or a side card), the composer's send is greyed out (typing still works) and a "重新生成" button sits centered right above the box (same as the footer's). A reply cut off with partial text is a normal turn.
- Editing an assistant reply → a new sibling version (same fork / thread / anchor), shown at once; the original stays untouched with its reasoning, follow-ups and side questions. The edited version has no reasoning (not shown, never echoed), no follow-ups or side questions of its own yet, and shows its source's request / response in details with a note and a "查看原回复" button. Editing an edited version makes another sibling whose history extends the chain. Why: overwriting has unsolvable edge cases — encrypted reasoning / signature checks, edit-then-revert leaving two heavily overlapping reasoning chains — and an overwrite can change the meaning so it contradicts the reasoning; one simple rule also keeps users from getting lost or looking up rules. Accepted cost: in a long conversation you can't fix an early mistake in place.
- Editing happens in a dialog: a user message (with its images) or a reply's plain Markdown source (no locks — the original keeps its anchors). Closing it with changes asks first (Esc / outside click / ✕ / Cancel). After sending / saving, the new node's top takes the old node's place on screen ("the new node's message top = the current node's message top"); the same for retry. A reply without text (failed, stopped early) can be edited too: the user writes one, saved as a new version like any edit; the version history then shows the original as "（没有回复正文）".
- Request detail = a dialog (dialogs leave far fewer layout cases than the old docked panel): ⓘ in the reply footer, "详情" on error boxes, main chat and side cards alike. Nothing behind it moves; Escape / outside click closes it (an expanded side card stays). "查看原回复" switches the chat behind it and shows that node's detail. Switching conversation closes it. The "历史版本" tab exists only on edited versions; its versions show in full (no inner scroll box). History reasoning folds with history messages.

### Scrolling and reasoning

- Scrolling (owner, step 7) — one set of rules for the chat and each side card's message area:
  1. The view moves on its own only while *following* (keeping the end of the messages in view as they grow); anything else that changes size leaves what's on screen where it is.
  2. Following turns on when the user sends or retries / edits, on switching conversation and when the user scrolls to the end; it turns off when the user scrolls away from the end, clicks a reasoning toggle / the switcher (they're reading what's on screen; otherwise the view jumped to the end once the hold ended — owner found this) or drags out a text selection in the area (following pulled the text from under the mouse). Nothing else changes it (content getting shorter doesn't). Only a press on the scrollbar counts as scrolling, not clicks on the content.
  3. Never pulled up: where content got shorter at the end, blank space is added at the bottom instead; trimmed away unnoticed.
  4. What the user clicks stays put for a moment: reasoning toggle, version switcher, the passage a side question / note is created from (the column may appear and narrow the chat — the text rewraps), a retry / edit (the new node's top where the old one's was, at least at the top; its reply is then followed only until that top reaches the top of the screen). Scrolling by hand ends it at once.
  Why one set: the first version had several independent mechanisms (follow, holds, blank, card reveal, auto-folding reasoning) that set each other off while streaming, and the owner found jumps.
- Reasoning: folded by default and opened / closed only by the user, also while it streams — never automatically. No inner scroll box — unfolded it shows in full; while it runs past the top of the screen its "思考过程" toggle sticks to the top of the scroll area (main chat or side card), so it can be folded from there, and folding keeps it at the top with the reply right below.

### Side questions, notes and the side panes

- Side questions: select text in a main-line reply (body only, not reasoning or user messages) → floating "追问" → a draft card expanded in the side-question column at the selection. Its input box is prefilled with the selection as a `> ` blockquote + blank line, so the user decides what gets quoted; context = root→node main path + the side thread, sent as typed. Side threads never enter the main context. A thread is a full mini-chat (follow-ups, retry, edit, ‹n/m›). No side questions inside side answers. Anchored text is highlighted; overlapping highlights show a picker listing both kinds.
- Card ⋯ menu (collapsed cards show it on hover; drafts have none): side question = 重命名 (shown at once, even while a naming request runs, which then leaves it alone) / 归档 (the whole thread); note = 归档 (once it has text). No confirms: archiving is reversible. Clicking an expanded card's header (not its buttons) collapses it; cards have no collapse button (Escape and the header do it).
- Side-question column: right of the chat inside its scroll area, scrolling with it.
  - Width depends only on the window and the user's dragged width: the chat stays centered while the column fits, else shifts left, then narrows; column 260–640 px, default 380, never leaving the chat under 420 px.
  - Collapsed card = title (naming dots) + ⋯ on hover; drafts show a small "草稿". Its top = its anchor's first line, pushed down only to avoid overlap; positions follow content resizes (0.2 s transition).
  - One card expanded at a time, at its anchor; it *covers* (doesn't push) the cards it overlaps (they fade out, their bars stay).
  - Every expanded card has a fixed height (min(75vh, scroll area − 32 px)): a side question's messages scroll inside with the same rules as the chat, a note's text / editor scrolls inside (owner, 2026-10-07: notes as tall as their text hung off the screen, typing pushed the chat up, 完成 / collapsing made it jump).
  - Expanding never scrolls the page; a card that wouldn't fit on screen below its anchor opens shifted up by just enough, fixed once open. Rejected: choosing only between opening down or up from the anchor (at 75vh a card then often overhangs the screen when its anchor is mid-screen; a half-screen card was too small).
  - Marker strip along the column's chat side (like VS Code's gutter change bars): a bar per anchor spanning its lines (overlapping anchors in side-by-side lanes), whether its card is visible or covered; tip = title · turns. Hovering a card / bar deepens its highlight and vice versa.
  - Clicking a highlight or a bar toggles its card (expanded → collapses, else expands, collapsing the one covering it).
  - Escape collapses (not while focus is in an input / menu / dialog — except the card's own input box with nothing typed: empty or still just the prefilled quote).
  - Drafts: an empty one (nothing beyond the prefilled quote) vanishes when its card closes; a typed one stays as a "草稿" card (text + images kept in memory per conversation); the first send makes it a thread.
  - A card whose thread leaves the path (archived, other branch) collapses; switching conversation collapses.
- Notes: selecting text in a main-line reply body or user message → the pill has "笔记" (replies: "追问 | 笔记"; user messages: only "笔记"). Creates an empty note and expands its card straight into editing. Same column and rules as side questions. Style = amber (highlights, bars, NotebookPen icon); collapsed card = icon + first line (Markdown markers dropped, muted); bar tip = first lines. Overlapping side question + note = indigo tint with both underlines. Expanded card: header (icon + 笔记, ⋯), rendered Markdown + "编辑"; editing = autosizing textarea (saved 400 ms after typing stops and on leaving) + hint "笔记只给自己看…" + "完成"; Escape in the editor = 完成, otherwise collapses. A note empty when its editor closes or its card goes away is deleted outright (not archived). Notes are never sent and stay on their node.
- Collapsible, resizable side panes (owner, 2026-10-07): the conversation list (left) and the side-question column (right) collapse and expand **only through their header buttons**; their width is dragged at their inner edge (list 200–420, default 256; double-click a handle = default). Open / closed and widths are global, persisted, unaffected by switching conversation. The right column, when open, takes its space even with nothing in it ("可以空展"); collapsed it leaves only the marker strip and the chat recenters. With the column collapsed, clicking a highlight / bar or creating a side question / note opens the column and the card — opening only, never closing it. Left collapsed: the chat header shows expand + new chat buttons. Right: its button is at the header's right end (after the tree map's); its drag handle sits over the column's left edge, the scroll area's height. Opening / closing slides (0.2 s; the list keeps its width and is clipped; the chat, input box and column move together).
- The main input box floats (owner, 2026-10-07: no background-colored bottom strip cutting off the chat and the column): the chat's scroll area and the side column reach the window's bottom; the box lies over the chat's bottom, the chat column's width less 12 px a side (messages: less 24 px), 16 px above the bottom, above the sticky reasoning toggle. Below the box and beside its lower half the background covers the messages (text needn't show under it); only above that do they pass visibly. The messages end above the box.

### Input

- Images (main chat, side questions, editing a user message): attach button, paste (only when the clipboard has no plain text, so copied spreadsheet cells still paste as text), or drop — onto the whole chat column / side card, or onto the message editor. Shown as thumbnails above the user bubble (click → full-size viewer). Sent before the text in each protocol's native shape (openai-chat `image_url` data URL, Responses `input_image`, Anthropic base64 `image` block); an image-only message has no text part; messages without images stay plain strings. Kept byte for byte when PNG/JPEG/GIF/WebP ≤ 5 MB and ≤ 8000 px a side (Anthropic's limits, the strictest); otherwise converted to PNG or downscaled JPEG. No per-model "supports images" check — a model that can't see images returns the API's error.
- Unsent text (and images) in the main input box stays with its conversation (owner, 2026-10-07): switching shows that conversation's own unsent text; the not-yet-created new chat has its own; in memory only, like side-question drafts (gone on reload). It used to carry over into the next conversation, where Enter sent it to the wrong one.
- User messages and notes render as Markdown, with single newlines kept as line breaks.
- No tool calling.

### Providers, models and parameters

- Protocols: OpenAI Chat Completions (base URL incl. `/v1`, → `/chat/completions`), OpenAI Responses (→ `/responses`), Anthropic Messages (base URL **without** `/v1`, as in Anthropic's SDKs, → `/v1/messages`; sends `x-api-key`, `anthropic-version`, `anthropic-dangerous-direct-browser-access`). Settings show the resulting request URL. No check for fields an API requires (e.g. Anthropic `max_tokens`): the API's own error shows in the chat (other vendors now speak the Anthropic protocol too, such rules won't last).
- Providers: **no defaults.** "Add provider" makes a blank form. The app adapts per *protocol*, never per vendor, and adds no optional request fields itself (not even `stream_options`); the request body is only the protocol's required fields + the model's parameter config (a preset may put optional fields there — the user chose it).
- Models: settings show the provider's models as a list (no text box). Clicking a row (anywhere but its delete ✕) or its gear opens that model's config dialog; "添加模型" opens the same dialog for a new model. The dialog edits a draft: Cancel (asks if changed) / Save; nothing is validated while typing, Save checks name, parameter JSON and header lines and lists every problem in one error notification. "从接口获取" adds new names, never removes; if the deduplicated list has ≥ 12 models it instead opens a dialog listing them all (search, an add button per row; already-added ones greyed). "Copy from another model" copies a whole config.
- Presets: built-in, one per protocol + model + channel (currently only vendors' official APIs). The config page's top card opens a picker listing every preset; its only tags are channel ("官方"), model family (DeepSeek / GPT / Claude) and protocol (no descriptive tags), filterable as chips (any within a group, all groups). Presets for another protocol than the provider's are greyed out and can't be picked. A preset holds only a model config (params, echo, headers) — no model id, no base URL (third-party channels may serve a model with the official parameter config, so a preset must be usable there too). Applying one **replaces** the model's whole config (confirm if it had any) and never touches the model name or the provider. No temperature control (fading out, rules too vendor-specific). "最大输出" is on by default at the model's maximum (owner, 2026-10-08: it's only a cap, and a low one cuts off long replies). Every preset's sources and reasons: `docs/presets-research.md`. The page notes whether the config still matches the preset.
- Model parameters (JSON in the format of `paramsDoc.ts`), per model. Four types — `choice`, `range` (min / max / step), `fixed`, `silent` (always sent, not shown). The first three have a name, optional `toggle` (+ `defaultOn`), `default`, and `requires` (`{name: true|false|value|[values]}`; chains allowed, cycles rejected). Switch semantics (owner's): a switch = optional (any param with `requires` always gets one); usable switch = no dependency restricts it; greyed switch (shown off) = unmet dependency, can't be sent, and the user's position returns once it's met; on = sent and its value control shown; off = not sent, value control hidden; no switch = always sent. Bodies deep-merge in config order; the protocol's own fields are rejected. Errors are reported when the config is saved, so a stored config is always valid (no UI for an invalid stored one; old data needn't be handled during development). The format guide dialog has a copy button.
- The model picker and parameter controls live in the composer's bottom bar (main chat and side cards alike). Parameter choices are remembered per provider + model.
- Echo-back ("回传思维链"; the *target* model's setting decides) and custom headers (`Name: value` lines, may replace built-ins case-insensitively; model listing sends none) are separate from parameters. Echo on with no fields chosen → automatic: openai-chat sends the first present of `reasoning_details` › `reasoning_content` › `reasoning` (only one, they duplicate each other); Anthropic all thinking + redacted_thinking blocks (before the text block); Responses its reasoning items (before the native message item, whose id is kept and text replaced). Chosen fields mean field names / block types / item types respectively (`*` = all). Echo goes only to the **same provider** that produced the reply (stricter than same protocol: another vendor's encrypted blobs / signatures are useless or rejected). Text always comes from what's displayed.
- Automatic naming: optional "命名模型" in Settings › General (any provider's model, sent with that model's parameter config; a "参数调节" button next to the picker sets choices used only for naming; off = first line of the message as title). A conversation is named from its first message + reply, once that reply finishes successfully; a side question from up to two main-line turns above where it was asked (as background) plus its root message + reply. Prompt = Chatbox's `nameConversation` (adapted wording for side questions), in the UI language, each message cut to 200 chars (Chatbox's 100 is too short for a quoted side question). While the reply or the naming request runs, the title spot (sidebar, chat header, side card header) shows bouncing dots. Failure (or the chosen naming model was deleted) → error notification and the first-line fallback, accepting that it repeats for every new conversation while the naming model is broken. A side card's header shows the thread title with a small "侧边提问" below (no icon).

### Archive, export and import

- Archive replaces every node deletion except deleting a whole conversation. Main-line reply footer ⋯ menu: "标注", "设为分支" (attempts only), "归档"; side nodes have no menu (a side thread is archived as a whole from its card). Archiving is disabled while the node or anything below it is streaming (tip says why); archiving what an expanded card shows (or something above it) collapses it. If the remembered child at a fork is archived, the newest remaining child shows; if none remains, the path ends there. Archiving leaves the remembered selection alone; restoring first pins what's shown at that fork, so restoring never switches the view.
- Archive dialog (conversation ⋯ menu → "查看归档"): entries newest first (archived main node, a whole side thread, or a note), each with kind (尝试 / 分支 / 侧边提问 / 笔记), first line (side: thread title or fallback), where it sits ("在第 N 轮「…」之后" / "问自第 N 轮「…」" / "在对话开头" / "在第 N 轮「…」的回复上 / 的提问上"), node count (not for notes), archive time, Restore and Delete. Restore is disabled (with a tip) while anything above it is archived (a note: while its node is hidden). Delete (danger confirm) deletes the entry's whole subtree (archived or not, side threads included), the notes on it, its remembered selections / titles, and unreferenced images; for a note, just the note.
- Export / import: one conversation at a time, as a JSON backup only (no Markdown). "导出" in a conversation's ⋯ menu; import button next to "新对话". The file (`format: "explore-with-llm/conversation"`, `version: 4`; nodes carry `branch` / `archived` / `label` as stored; `notes` = all its notes, archived included) has the conversation, **every** node (all branches, side threads, edited versions) with the full raw request records, and its images as base64. API keys are removed: credential-like header values become `[removed]`, and any known provider key or credential header value is scrubbed from every string. Import accepts versions 1–4 (v1: `branch` derived like DB v5; v1/v2 have no notes; v1–v3 no labels), validates the file (incl. `branch` / `archived` / `label` types and note shape), gives every id (conversation, nodes, threads, images, notes, `[image:<id>]` markers) a new one so importing twice makes two copies, marks `streaming` nodes `aborted`, sets `updatedAt` to now and opens it. `providerId` is kept, so echo-back works only if that provider exists in this browser.

### Feedback, help texts and style

- Errors: a failed action the user just took (import, unreadable image, model fetch, saving a model config) → error notification (top right, stays until closed). A chat request's errors stay in the chat as the red error box with Details (HTTP errors, stream error events, network, connection dropped mid-reply with the partial text kept, empty reply). No request timeout (reasoning models can think for minutes); before the first output the reply shows "已等待 N 秒" after 5 s. A standing problem the user isn't looking at (e.g. the naming model was deleted) → one error notification when it matters (here: when a title was due); an identical notification already open isn't shown again (notifications stay until closed, so once is enough). Every error message names what it is about (e.g. "自定义请求头：第 1 行…").
- Success: so far always a brief in-place confirmation (the button turns into ✓ + text for ~1.5 s, like copy buttons and "✓ 获取成功") or simply the visible result (dialog closes, list updates, conversation opens).
- Help texts: consequences the user needs while deciding stay visible (request URL preview, "API Key 只保存在浏览器", edit-mode notes, state notes in the detail dialog); explanations of how something works go behind a hover question mark (`HelpTip`; a click pins it open until the next click on it, a click elsewhere or Escape); anything the UI already makes obvious is removed. Tooltips are always the app's `Tip`, never a native `title`.
- UI languages: zh + en. Desktop only. Light and dark themes (the owner was willing to drop dark; it stays).
- UI should be clean and polished but not complex.

## Engineering principles

- **Before building** (owner, 2026-10-08): first check whether the request fits the existing framework — which shared concerns it touches, and whether it can go only through their owners and existing libraries without bending a Product decision. If it fits, just build it. If it needs a new mechanism, a change to a shared concern's owner, or bends / conflicts with a Product decision, stop before writing code: explain the options to the owner in plain words, with what each costs (behavior, risk, effort), and a recommendation; build what the owner picks. The same assessment sets the verification level (Verifying changes).
- Before writing anything general-purpose, look for a mature library (installed ones first, e.g. Radix for overlays). Write our own only where nothing fits, and say why here. (Owner: "borrow predecessors' wisdom, don't reinvent wheels".)
- One owner per shared concern: data reads `useConversationData`; scrolling `useAutoScroll`; Escape / outside clicks `Layer` + Radix primitives; focus `lib/focus.ts` + `Dialog`; conversation switch `setConversation` + `ChatView`'s reset; layout widths `columnFrame`. No second mechanism beside it.
- Derive, don't store a second copy (colors are computed from the tree; the streamed-text race came from two copies of the same text).
- Tests guard the rules of these foundations (e.g. the scroll suite), not one test per reported bug.
- Library decisions (foundation pass, 2026-10-07):
  - Scrolling: kept `useAutoScroll` after reading `use-stick-to-bottom` 1.1.6's source. It only sticks to the bottom: no holds, no blank space (it clamps the view back down — the opposite of rule 3), re-locks following when content shrinks near the end (against rule 2), observes only the content box. Adopting it would put a second scroll writer beside our hold / blank code — what broke scrolling before. Virtualizing lists (react-virtuoso `followOutput`, virtua) not tried: they'd take over rendering for one feature.
  - Selection pill: Floating UI (`@floating-ui/react-dom`, the version inside Radix) with the selection as a virtual reference. Not Radix Popover: its anchor is one box, and only Floating UI's `inline` middleware centers on the first line (or last, when flipped below) of a multi-line selection. The overlap picker is a Radix menu at the click point.
  - Not changing: tree map layout (classic tidy algorithm, tested; d3-hierarchy only if the map grows), side-column layout math (our own design, no library fits), pane resize handle (see Architecture › panes), Dexie / Zustand (already libraries).
